# 性能

对 Hook 库来说，性能不仅是单个函数的大小，还包括依赖图是否清晰，以及浏览器中存活的原生工作是否可控。官网只记录可以从发布产物验证的事实，不对未知的使用方应用作无依据的承诺。

## 选择明确的包入口

每个 Hook 都有 `better-hooks/use-media-query` 这样的独立 ESM 入口，同时保留根入口。直接导入能明确模块归属，也让构建工具从调用方需要的最小依赖图开始。包除了 React peer dependency 没有其他运行时依赖，并声明 `sideEffects: false`。

这些是可验证的包属性，并不表示每种打包工具或每个应用都会得到完全相同的输出结果。

## 在所有权清晰时共享原生工作

只要所有权与清理规则保持明确，外部状态源 Hook 就会共享底层原生工作。同一 `Window` 中相同的媒体查询会复用一个条目；联网状态在每个浏览器上下文中共用一对监听器；窗口尺寸则由当前订阅者共用一个 `resize` 监听器。

## 提交后调度，先清理再报错

定时器和监听器只在组件提交后建立，并在依赖变化或组件卸载时清理。稳定的回调 ref 可以避免仅因函数引用变化就重建原生监听器。

异步、定时和事件回调也会先清理内部任务，再让错误离开回调。`onError` 观察器可以检查失败，但不能替换原始抛出或 Promise 拒绝；已经过期或取消的任务可按相应 Hook 契约抑制错误。

## 测量发布产物

官网不会发布缺少依据的竞品对比或合成基准数据。只有数据来自当前构建，并明确标注入口、压缩方式与版本时，才会展示包体积数字。未经验证的数字宁可不展示，也不会用过期的占位数据代替。
