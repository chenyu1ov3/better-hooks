# ADR 002 — API semantics

## Status

Accepted.

## Context

Small Hook APIs become hard to compose when actions change identity, callbacks become stale, or cancellation behavior is implicit.

## Decision

Actions returned by Better Hooks remain stable where their semantics allow it. Long-lived work calls the latest committed callback. Async and debounced work expose cancellation where callers need control, and stale asynchronous results cannot replace newer state.

Controlled and uncontrolled state share one setter contract. Functional updates receive the latest value owned by that mode, and `onChange` is not called for `Object.is`-equal updates.

Errors follow a propagation-plus-observability contract. Hook callbacks do not
silently swallow failures: timer, native-event, and promise callbacks clean up
their internal work first, notify the optional `onError` observer, and then
preserve the original throw or rejection. Cancellation and stale-run guards may
intentionally suppress errors from work that is no longer current.

If an `onError` observer throws, the Hook still preserves the original error.
The observer failure is reported in a microtask so it cannot replace the
original throw or promise rejection.

React Error Boundaries only handle errors thrown during render, lifecycle
methods, and constructors in their descendant tree. They do not catch errors
from a timer, a native event listener, or a promise callback. Applications that
need a boundary for those sources should bridge the error into render state (or
use the hook's `onError` observer) explicitly.

## Consequences

Implementation refs are updated at commit boundaries. APIs may expose a small state object rather than a bare callback when status or cancellation is part of the contract. Documentation describes leading, trailing, reset, and fallback behavior explicitly.

Cleanup is part of the error contract: a failed callback cannot leave a pending
timeout, interval, debounce window, lock, or event subscription active unless
the API explicitly documents that behavior. Render-phase errors remain the application's responsibility and can be handled by a React Error Boundary.
